# OpenMotion onboarding

Follow the [shared installation contract](../../docs/install-onboarding.md#installation-success-reply). Complete its four parts in this installing turn: open the library, display the maintained welcome above three full-video cards, and automatically connect this chat to the installed workspace. Registration and an independent MCP probe are not current-chat activation.

1. **Reuse the installation.** Source setup returns `inlinePresentation`, `preview`, `hostHandoff`, `detailsFile` and, for a known chat, `recovery`. npm setup wraps these in `onboarding`. Preserve the application, workspace, language and frozen random three-of-nine IDs/order. If no setup result exists, run the installed `node --experimental-strip-types scripts/install-onboarding.mjs` once with the connection's workspace and the latest request's `OPENMOTION_ONBOARDING_LANGUAGE`. Never reinstall or enqueue a new user message.
2. **Activate this chat.** Use working native discovery and `openmotion_get_project` first; its workspace must match. Otherwise follow the supported existing-host reload. For `refresh_requested`, let the current host tool step finish, then run `recovery.command` with `recovery.args` once in this same turn. Recovery verifies the same selection, resource and workspace without another reload or library startup. A missing control endpoint is a host integration dependency. Do not start another app-server, change host security, restart Codex, or ask the user to restart a connection as a substitute for automatic activation.
3. **Open the library once.** Use the exact `preview.previewUrl` in this chat's right-hand browser, preserving query parameters and reusing the existing tab. Mark it as a deliverable when required by the browser tool. Opening is sufficient: no template inventory scan, screenshot audit or full-video playback check is needed for installation. Do not create a project.
4. **Deliver the native welcome and video cards.** For `native_required`, call the natively discovered `openmotion_show_template_recommendations` once with the prepared IDs/order, request language and `onboarding:true`. The persistent conversation component contains the maintained welcome above exactly three full-video cards. Do not duplicate it in the final reply, put it only in collapsed commentary, replace videos with text cards, substitute builtins or resample. If the welcome already appeared, append `--welcome-delivered` to the recovery command and use its cards-only `onboarding:false` arguments. Verify the current discovered tool accepts the selection and advertises the prepared immutable resource URI. Actual audiovisual acceptance remains a separate user check.

If native presentation is blocked, output the maintained introduction as ordinary final-reply text and include the real library link, followed by the concrete blocker. Do not omit the welcome or imply that missing video cards were delivered. The current fixed-CSP document renderer cannot load the reference-video origin; a right-hand library or shell Tool call is not a substitute. No card-video guarantee is possible until a compatible native connection exists. Keep onboarding incomplete and preserve the receipt.

Self-contained builtin fragments retain the contract's compatibility path; they are not the default nine-reference onboarding and never replace its selected references. A readable prepared file does not prove visible delivery.

Use `zh`, `en`, `ja`, `ko`, `fr`, `es` or `pt` from the latest user request, otherwise `en`. Recreate prepares an unsent draft through a negotiated host extension, or copies the brief with a floating Toast. Only the user-sent brief authorizes creation/export. Continue an accepted recommendation through [accepted template selection](../../docs/install-onboarding.md#accepted-template-selection).
